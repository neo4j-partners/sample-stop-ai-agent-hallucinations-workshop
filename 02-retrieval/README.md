# Lab 2: Retrieval, with and without the graph

[![Strands Agents](https://img.shields.io/badge/Strands_Agents-1.27+-00B4D8.svg?style=flat)](https://strandsagents.com)

Four retrievers run in pairs against the graph Lab 1 built, each pair on the same question with the same embedding, so the connected-context delta is watched rather than described. The lab closes with the production retriever handed to an agent and asked a question the graph cannot answer.

**The mechanism, in one sentence: vector search finds candidates, traversal finds what is connected.**

**At a Glance**
- **Failure it stops:** text that merely looks relevant standing in for connected facts, and an agent guessing past the edge of what the graph knows.
- **Neo4j:** the `hotel_chunk_embeddings` vector index, the `hotel_chunk_fulltext` full-text index, and one reviewed Cypher traversal.
- **AWS:** Amazon Nova 2 embeds each query, and Amazon Bedrock runs the small grounded agent that closes `2.2`.
- **You'll build:** nothing in the graph. This lab only reads it.

## The three notebooks

| Notebook | The pair | What it proves |
|---|---|---|
| [`2.1_vector_retrievers.ipynb`](2.1_vector_retrievers.ipynb) | `VectorRetriever` against `VectorCypherRetriever` | The same vector search, with and without a traversal, returns the same text and different context |
| [`2.2_fulltext_retrievers.ipynb`](2.2_fulltext_retrievers.ipynb) | `HybridRetriever` against `HybridCypherRetriever` | Full-text matching holds an exact identifier a vector arm blurs, and the traversal supplies the facts neither arm carries. Closes on abstention |
| [`2.3_text2cypher.ipynb`](2.3_text2cypher.ipynb) | Optional. `Text2CypherRetriever` alone | Neo4j computes a count over the whole matching set, which top-k retrieval cannot do |

Run `2.1` then `2.2`. `2.3` is optional and can be skipped for time; nothing later in the workshop depends on it.

### `2.1_vector_retrievers.ipynb`

`VectorRetriever` is the standard-RAG baseline. It embeds the question, finds the nearest `:Chunk` nodes, and returns their text. The notebook asks for the standard check-in time at AnyCompany Cairo Nile View, a paraphrase that exact matching would miss and semantic similarity finds.

`VectorCypherRetriever` runs the identical search over the identical index, then hands each match to reviewed Cypher that walks from the chunk to its hotel and out to that hotel's rooms, amenities, policies, and services, capped at twelve related items. No part of that Cypher is generated by a model, and no part of the question is interpolated into it.

Both retrievers find the same chunks. Only the second returns `guest_rating` as a named field and the amenity list as a list. An agent handed `guest_rating: 4.5` cannot round it down or invent a five, and a write path handed `hotel_id` can act on the right hotel without matching a display name.

### `2.2_fulltext_retrievers.ipynb`

Embeddings blur exact strings. A postal code, a confirmation number, and a SKU all embed to roughly "short numeric token", so a question containing one returns chunks about the right topic and the wrong record. The notebook asks for the cancellation policy of the hotel at postal code `60611` and runs it two ways: `VectorRetriever` alone for the semantic-only comparison, then `HybridRetriever` fusing a vector arm and a Lucene full-text arm. An assertion at the end fails if the correct chunk is absent from the hybrid results, which is the honest part of the comparison.

`HybridCypherRetriever` is that fusion plus the traversal from `2.1`, and it is the one retriever the rest of the workshop uses. It is therefore not built inline. It lives in [`workshop/src/workshop/hybrid_retrieval.py`](../workshop/src/workshop/hybrid_retrieval.py) behind a function that accepts exactly one field:

```python
search_hotel_knowledge(query: str) -> list[HotelEvidence]
```

Fusion is `NAIVE`, `top_k` is fixed at 5, at most twelve amenities come back, and the traversal is the same reviewed Cypher every time. There is no ranker, alpha, top-k, or retriever-mode parameter for a caller to set. Those comparisons are the ones the participant just ran by hand; a request does not get to re-run them. Lab 3 puts this function behind a Strands `@tool`, Lab 4 writes against the `hotel_id` it returns, and Lab 5 deploys it unchanged.

The hero question, *"What amenities and guest rating does AnyCompany Cairo Nile View have?"*, makes every arm earn its place. The exact hotel name is what the full-text arm is for, "amenities and guest rating" is a paraphrase of the document's own wording and is what the vector arm is for, and the rating and the amenity list are in neither matched chunk. The traversal is what produces them.

## The abstention is the point of the lab

`2.2` closes by handing that one retriever to a small Strands agent carrying the workshop's grounding instructions, asking the hero question, then asking:

> *"Does AnyCompany Cairo Nile View guarantee room availability next weekend?"*

The graph knows the hotel and does not know the availability fact. The retriever returns hotel evidence and no availability evidence, so the agent says it cannot determine the answer instead of reading "subject to availability" as a yes.

This is the one unanswerable case the lab runs, and it is deliberately the hard version. An off-corpus question such as a hotel in Antarctica is easier, because a plain vector index also handles an off-corpus query badly. The availability question is the shape participants meet in production: the entity is present, the fact is not. Prompt patterns for refusal, confidence thresholds, and score cutoffs stay out of this lab.

## This lab reads the graph, it does not build it

Nothing here creates a node, a relationship, an index, or an embedding. Every artifact these notebooks need comes from [`01-graph-build/1.1_build_graph.ipynb`](../01-graph-build/1.1_build_graph.ipynb).

Each notebook opens with the same verification cell. It confirms the Neo4j and AWS credentials are present, then calls `verify_retrieval_indexes` and `fixture_problems` from [`workshop/src/workshop/retrieval_setup.py`](../workshop/src/workshop/retrieval_setup.py). The first requires both indexes to be `ONLINE` with the expected label, property, dimensions, and similarity function. The second checks the specific graph facts the questions below it depend on, including the Windward Mile Tower chunk that carries `60611`. Either check failing raises with the missing piece named and one instruction: run Lab 1 first.

When credentials are absent, the cell prints what is unset and every live cell below it skips, so all three notebooks run top to bottom offline.

### The embedding constants have exactly one definition

A query embedding has to come from the same model, at the same dimension, with the same purpose as the vectors Lab 1 wrote. A mismatch does not raise. It returns confident, wrong neighbours. So the notebooks import the constants from [`workshop/src/workshop/retrieval_contract.py`](../workshop/src/workshop/retrieval_contract.py) and never restate them locally:

| Constant | Value |
|---|---|
| `EMBEDDING_MODEL_ID` | `amazon.nova-2-multimodal-embeddings-v1:0` |
| `EMBEDDING_PURPOSE` | `GENERIC_INDEX` |
| `EMBEDDING_DIMENSIONS` | `1024` |
| `CHUNK_VECTOR_INDEX` | `hotel_chunk_embeddings` |
| `CHUNK_FULLTEXT_INDEX` | `hotel_chunk_fulltext` |

The embedder itself is constructed from `workshop.bedrock_providers`, the same module the build used.

## Quick Start

### Prerequisites

- Python 3.12+ and the [uv](https://docs.astral.sh/uv/) package manager
- The repo-root `.env` filled in, per [`00-setup/README.md`](../00-setup/README.md)
- Lab 1 finished, so the graph, both indexes, and the fixtures exist
- Amazon Bedrock access for Amazon Nova 2 embeddings and for the model the closing agent uses

### Install

```bash
cd 02-retrieval
uv venv && uv pip install -r requirements.txt
```

`requirements.txt` holds two lines. `-e ../workshop` brings the shared package, the embedder, and the index names. `strands-agents` is there for one reason: `2.2` closes by handing the retrieval tool to an agent, which is the first time in the workshop a model is asked to decline rather than guess.

### Run

Open `2.1_vector_retrievers.ipynb`, then `2.2_fulltext_retrievers.ipynb`, then optionally `2.3_text2cypher.ipynb`, in VS Code, Kiro, or any editor with notebook support, and run the cells in order.

### Check that the notebooks execute

This folder has no Python tests. The honest check is the shared notebook runner, from the repository root:

```bash
uv run setup/run_notebooks.py --labs 2
uv run setup/run_notebooks.py --list
```

The runner is a PEP 723 script, so `uv` manages its own cached environment and there is no separate install step. `--labs 2` executes all three notebooks into a temporary copy, leaves the sources untouched, and exits nonzero if any cell raises. It creates no AWS resources. A clean run proves the cells did not raise; it does not validate the narrative claims above unless the notebook itself asserts them, which `2.2` does for the `60611` result.

## Troubleshooting

**A retriever returns nothing.** Confirm which question. An empty result on the availability question at the end of `2.2` is the designed outcome, not a fault. An empty result on the check-in, `60611`, or hero questions means the graph is missing or was built from a different corpus. The verification cell at the top of the notebook names the absent fixture, in the form `Windward Mile Tower hotel at postal code 60611: found 0, expected at least 1`. Re-run Lab 1 and let it finish.

**A missing or offline index.** `verify_retrieval_indexes` raises `Retrieval index check failed:` followed by one line per problem, such as `missing index 'hotel_chunk_embeddings'` or an index in a state other than `'ONLINE'`. Lab 2 never creates indexes. Lab 1 creates both, idempotently, and waits for them to come online. Re-run it.

**A dimension mismatch.** The same check reports `index 'hotel_chunk_embeddings' has 384 dimensions, expected 1024` when the graph was built with a different embedding model or a different dimension. Do not change the constants to match the index. The vectors themselves are wrong for the retrieval contract, so rebuild in Lab 1 with `workshop.retrieval_contract` unmodified. A similarity-function mismatch reports the same way and has the same fix.

**Bedrock access denied on the query embedding.** Enable `amazon.nova-2-multimodal-embeddings-v1:0` in your region through the [Bedrock Model Access console](https://console.aws.amazon.com/bedrock/home#/modelaccess), and confirm `AWS_REGION` in the repo-root `.env` matches the region where it is enabled.

**Cells print "Skipping" and nothing runs.** `NEO4J_URI`, `NEO4J_USERNAME`, or `NEO4J_PASSWORD` is unset, or no AWS credentials were found. The cell names which. Note that the hosted Workshop Studio environment writes `NEO4J_USER` while every lab reads `NEO4J_USERNAME`.
